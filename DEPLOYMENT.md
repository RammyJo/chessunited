## 0. What is deployed

Two Cloudflare targets serve the same `dist/` build:

1. **Cloudflare Pages, project `chessunited`** — the production host, served at
   `https://chessunited.pages.dev`. Uploaded directly from `dist/` with Wrangler,
   so `dist/_headers` (CSP, security and cache rules) applies natively.
2. **Freebuff Sites** — the mirror, a managed Worker plus static assets declared
   in `deploy.json`. `scripts/make_worker.mjs` embeds the same `_headers` rules
   into the Worker so both hosts answer identically.

Wrangler's OAuth session is stored in the user's own Wrangler config
(`%APPDATA%\xdg.config\.wrangler\config\default.toml`), never in this repo. No
API token, account key or secret belongs in the project.

`deploy.json` (project root) points the mirror at:

- `sites/worker.generated.js` — generated by `scripts/make_worker.mjs` on every
  build. It serves `env.ASSETS`, applies the CSP, security and cache headers from
  `dist/_headers`, and answers missing URLs with `404.html` and HTTP 404.
- `./dist` — the Astro build output (HTML, `_astro/`, images, fonts, calendar,
  sitemap, robots, manifest).

Live responses were checked for the CSP and security headers, the 404 status, the
canonical host, `robots.txt`, the sitemap, the `.ics` MIME type and image caching;
see `QA_REPORT.md` §3.

## 0a. Redeploy after a content change

```powershell
npm run check
npm run build          # also regenerates calendar, headers, CSP hashes, worker
npm run qa
npm run qa:csp
```

Production (Cloudflare Pages):

```powershell
npx.cmd wrangler pages deploy dist --project-name chessunited --branch main --commit-dirty=true
```

Mirror (Freebuff Sites): deploy `dist/` again with `deploy.json`. Publishing is
a separate step from deploying: a new deployment does not re-publish an
environment that was taken offline.

If the site moves to a custom domain, set `SITE_URL` in
`scripts/site-url.mjs` (or the `SITE_URL` environment variable), rebuild and
redeploy so canonical, Open Graph, sitemap, `robots.txt` and calendar URLs match.
The committed default is already `https://chessunited.pages.dev`.

## 0b. Rollback

The host keeps deployment history. Roll back by redeploying the previous build,
or by restoring the last known-good `dist/` from Git and redeploying it. Because
`dist/` is generated, the reliable rollback unit is a commit: check out the
previous commit, run `npm ci && npm run build`, and deploy again.

## 1. Before deploying

1. Confirm the final production URL. The current live URL is
   `https://chessunited.pages.dev` (the default in `scripts/site-url.mjs`).
2. Build with that URL:

   ```powershell
   $env:SITE_URL = "https://your-final-host.example"
   npm.cmd run build
   ```

   `SITE_URL` changes canonical links, Open Graph URLs, `robots.txt`, the
   sitemap and the `.ics` calendar links. The calendar files are regenerated by
   `npm run build`.
3. Run the release checks:

   ```powershell
   npm.cmd run check
   npm.cmd run qa
   npm.cmd run qa:csp
   ```

   For browser checks, start `npm.cmd run preview -- --host 127.0.0.1 --port 4321`
   in another terminal, then `npm.cmd run qa:browser`.
4. Deploy only with the club's explicit approval. A deployment publishes the
   site publicly.

## 2. Cloudflare Pages settings

If connecting a Git repository or using the dashboard's direct upload:

| Setting | Value |
| --- | --- |
| Framework preset | Astro |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Root directory | repository root (leave blank if the repo is the site) |
| Node version | `24` (or current LTS 22+) via `NODE_VERSION` |
| Production URL variable | `SITE_URL` = final URL |

`npm run build` is self-contained: it regenerates the calendar with Node, runs
`astro build`, then writes `_headers`, CSP hashes and `robots.txt`. It does
**not** require Python. Python/Pillow are only needed to regenerate images
locally.

If `SITE_URL` is set in Cloudflare, set it for the **production** environment to
the final domain. Preview deployments will then also canonicalize to production;
if preview canonical URLs matter, set a separate preview value such as the
preview hostname.

## 3. Direct upload with Wrangler — **done, this is how the site ships**

No Git repository is needed for this path, which is how `chessunited.pages.dev`
was created and is kept up to date.

```powershell
npx.cmd wrangler login                    # browser consent, ~2 min window
npx.cmd wrangler pages project create chessunited --production-branch main
npm.cmd run build
npx.cmd wrangler pages deploy dist --project-name chessunited --branch main --commit-dirty=true
```

Wrangler's OAuth consent link expires quickly. If `Timed out waiting for
authorization code` appears, run `wrangler login` again and approve the new link.

Notes:

- `wrangler login` opens a browser for Cloudflare authorization. Do not paste an
  API token into source, a log or a document.
- If `chessunited` is already taken as a Pages project name, choose another name.
  The resulting URL is `https://<project-name>.pages.dev`; set `SITE_URL` to that
  URL and rebuild before deploying.
- Wrangler writes local state under `.wrangler/`; it is gitignored.
- If using a scoped API token instead of browser login, put it in the
  `CLOUDFLARE_API_TOKEN` environment variable for the command only. Never commit
  it.

   branches can create preview deployments.

## 5. Custom headers and cache behavior

Cloudflare Pages reads `dist/_headers` automatically. The generated file sets:

- `Content-Security-Policy` with SHA-256 hashes for the inline JSON-LD; no
  `'unsafe-inline'` for scripts.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy`, `Permissions-Policy` and `Cross-Origin-Opener-Policy`.
- HTML: `max-age=0, must-revalidate`.
- Fonts: one-year immutable cache.
- Images: 30-day cache with stale-while-revalidate.
- Calendar and scripts: one-day cache.

If you replace an image but keep its filename, the 30-day image cache may serve
the old file to returning visitors. Rename the output or purge the Cloudflare
cache after such a change.

`astro preview` does **not** apply `_headers`; `npm run qa:csp` simulates them
locally.

## 6. Post-deploy verification

Run these against the real URL, not localhost:

```powershell
curl.exe -I https://<final-host>/
curl.exe -I https://<final-host>/events/
curl.exe https://<final-host>/robots.txt
curl.exe https://<final-host>/sitemap-index.xml
curl.exe -I https://<final-host>/calendar/chess-united-tournament-2-0.ics
```

Check:

- [ ] `/` returns 200 over HTTPS and the canonical host is correct.
- [ ] `Content-Security-Policy` is present and there are no browser console CSP
      errors.
- [ ] `/robots.txt` points at the final sitemap URL.
- [ ] `/sitemap-index.xml` lists 7 public pages and no `/404`.
- [ ] `/calendar/*.ics` returns `text/calendar` and opens in a calendar app.
- [ ] The Messenger group link and both Maps links open.
- [ ] The Visit-page QR scans to the club's Messenger group.
- [ ] A nonexistent URL returns the custom 404 with HTTP 404 and `noindex`.
- [ ] Lighthouse production run meets the targets in `QA_REPORT.md`.
- [ ] No mixed content, no third-party requests, no unexpected cookies.

Then record the production URL, deployment ID and date in `QA_REPORT.md` and
update `SITE_URL` if the host changed.

## 7. Rollback

Cloudflare Pages keeps deployment history. In the dashboard, open the project →
**Deployments** → choose the last known-good deployment → **Rollback**. For a
direct upload, rebuild the previous commit or `dist/` and upload again.
